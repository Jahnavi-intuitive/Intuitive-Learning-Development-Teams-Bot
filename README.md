# L&D & Certification Agent — local build

Local-dev implementation of the agent + backend from BRD-LND-001 v2.0,
Sections 6/7/4, through this build's Phase 3 (data layer, backend tool
endpoints, ADK agent, test UI). Not built yet: Entra ID/Graph auth, Teams
SDK/Azure Bot Service, the reminder/notification engine, the leadership
dashboard. See `DEVELOPMENT_LOG.md` for the full decision history —
including two things worth reading before touching this: why there's no
Docker involved, and why there's a `curl_transport.py` in both `backend/`
and `agent/`.

**Status as of 2026-08-24: fully running and verified against real data.**
Employees, catalog, learning paths, KB content, and two real Credly-
verified submissions are seeded; the agent has been chat-tested end to end
including tool-calling. Everything below reflects how it's actually running
right now, not a plan.

## Layout

```
backend/     FastAPI service — owns the tracker, verification, KB, escalations, audit log,
             the agent proxy (app/routers/agent_proxy.py), and serves frontend/ as static files
agent/       ADK-based agent (adk_agent/) that calls the backend as tools
frontend/    the actual UI — single-page vanilla HTML/CSS/JS, no build step, served by the backend
test_ui/     retired — the old Streamlit dev UI. Stopped, kept on disk, not the way to use this anymore.
scripts/     seeding / one-shot cleanup / seed_data/*.json (researched catalog+path+KB content)
tools/       pg0.exe (embedded Postgres+pgvector) and a couple of one-off diagnostic scripts
data/trackers/   the certification tracker .xlsx (generated, not hand-authored)
```

Three things run, not four: `pg0.exe` (database), the backend (API +
agent-proxy + serves the frontend, all one process on `:8000`), and the
ADK agent server (`:8001`). Open `http://localhost:8000/` — that's the
whole app.

## Moving this to another machine

```
scripts\setup_new_machine.ps1
```

Downloads `tools/pg0.exe` if it's not already there, starts it, and
restores `scripts/db_dump/full_dump.sql` — a real `pg_dump` of everything
currently seeded (employees, catalog, learning paths, KB content with its
real embeddings, the 2 real verified Credly submissions). Only restores
into a genuinely empty database, so it's safe to re-run; pass `-Fresh` to
wipe and start over. After that, fill in `GEMINI_API_KEY`/`GOOGLE_API_KEY`
in the `.env` files (these don't travel with the dump — copy them by hand
or re-add the key) and follow "Run the backend" / "Run the agent" below.

If you seed more data later and want the dump to reflect it, run
`scripts\export_db_dump.ps1` to refresh `full_dump.sql`.

## No Docker — this runs on native Postgres via `pg0`

Docker Desktop turned out to be a dead end on this machine (WSL2 needs
hardware virtualization, which is disabled in BIOS/UEFI — a firmware-level
setting, not something fixable from Windows). Instead: `tools/pg0.exe` is a
single-binary, zero-install PostgreSQL 18 + pgvector 0.8.5 build
([vectorize-io/pg0](https://github.com/vectorize-io/pg0)). `docker-compose.yml`
is still in the repo (untested, in case Docker becomes available on some
other machine later) but isn't part of the actual working setup.

**Start the database:**
```
tools/pg0.exe start --port 5432 --username lnd_app --password change_me_locally --database lnd_certification
```
This matches `DATABASE_URL` in `.env`/`backend/.env` exactly, so nothing
else needs to change. Data persists across restarts under `~/.pg0/`. Leave
it running in its own terminal (or background it) — it's a real Postgres
server, not a one-shot command.

## One-time setup

1. `.env` (repo root) and `backend/.env` and `agent/.env` already exist
   with the real Gemini API key and matching DB credentials — see
   `.env.example` files for what's expected if you need to recreate them.
2. `data/trackers/certification_tracker.xlsx` already exists (generated by
   `scripts/generate_tracker_template.py` from `scripts/seed_data/*.json` —
   one sheet per certification, headers only, no fabricated rows).

## Run the backend

```
cd backend
python -m venv .venv                       # if not already created
.venv/Scripts/pip install -r requirements.txt
.venv/Scripts/python -m alembic upgrade head
.venv/Scripts/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Health check: `curl http://localhost:8000/health`.

**Important**: `app/services/embeddings.py` applies
`app/services/curl_transport.py` at import time — see the "TLS blocker"
note below. This is not optional/removable without breaking KB embedding
calls on this machine.

To sync the Excel tracker into Postgres:
```
curl -X POST http://localhost:8000/api/admin/sync-tracker
```
(Admin action — not exposed in the frontend UI, which is employee-facing.)

## Run the agent

```
cd agent
python -m venv .venv                       # if not already created
.venv/Scripts/pip install -r requirements.txt
.venv/Scripts/adk telemetry disable        # first run only — otherwise api_server blocks on an interactive prompt
.venv/Scripts/adk api_server --port 8001 .
```

Serves the agent (app name `adk_agent`) over REST on `:8001` — session
create at `POST /apps/adk_agent/users/{id}/sessions/{id}`, message send at
`POST /run`. `adk_agent/__init__.py` applies `curl_transport.py` before
importing `agent.py` — same reason as the backend, see below.

## Use the app

Nothing extra to run — once the backend is up (which also serves
`frontend/index.html`) and the agent is up, open **http://localhost:8000/**.
Chat is the primary interface. Saying you want to submit/log/update a
certification opens an inline form in the chat itself (via the agent's
`open_certification_form` tool) rather than sending you to a separate
page; the "Submit a certification" quick-action chip above the chat input
does the same thing instantly, without waiting on the LLM. "My Tracker"
opens a side panel that only fetches data when you actually open it.

`test_ui/` (Streamlit) is retired — superseded by `frontend/`, kept on disk
for reference but not maintained going forward.

## The TLS blocker, and why there's a `curl_transport.py`

On this machine, Python's OpenSSL-based HTTPS (used by both `requests` and
`httpx`) gets silently terminated mid-handshake for several destinations —
Gemini's API, GitHub's API, Google's homepage — regardless of network
(confirmed on two separate networks). PyPI is unaffected, and `curl.exe`
(Windows' native Schannel TLS) reaches every one of the blocked hosts fine.
This is almost certainly host-based security software recognizing/
allow-listing known TLS stacks rather than a bug in this code — see
`DEVELOPMENT_LOG.md`'s 2026-08-24 entries for the full diagnostic trail.

Fix: `backend/app/services/curl_transport.py` and
`agent/adk_agent/curl_transport.py` monkeypatch `requests`/`httpx`
respectively to shell out to `curl.exe` for every HTTP call, reusing the
TLS stack that's proven to work. If you move this project to a machine
where Gemini API calls work normally over plain `requests`/`httpx`, these
patches are harmless no-ops in terms of correctness but add subprocess
overhead per call — safe to rip out at that point (delete the file, remove
the `curl_transport.apply()` call and import), but no urgency either way.

## Seed data (already run once on this machine — for a new machine, use setup_new_machine.ps1 above instead)

```
python scripts/seed_test_employees.py       # the 5 real test employees (role is None — not asked for, not used by any logic)
python scripts/seed_catalog_and_paths.py    # catalog + learning paths + KB, from scripts/seed_data/*.json
python scripts/seed_real_submissions.py     # Puja Rachchh's 2 real, Credly-verified Google Cloud badges
```

Current seeded state: 5 employees, 48 catalog entries, 4 learning paths
(one per practice), 51 learning-path items, 48 KB items (real Gemini
embeddings), 2 real verified certificate_records for Puja Rachchh.

`seed_catalog_and_paths.py`'s catalog upserts are safe to re-run.
`/api/admin/learning-paths` is NOT an upsert — re-running the whole script
creates duplicate learning_paths rows (this happened once already, from a
partial run that failed partway through before the TLS fix; cleaned up
manually in Postgres). If you need to re-run it, delete existing
learning_paths/learning_path_items for the affected practice(s) first.

To remove all test data in one shot:
```
tools/pg0.exe psql -f scripts/delete_test_data.sql
```
